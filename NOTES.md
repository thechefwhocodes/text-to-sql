# Notes

The rest of the write-up that doesn't belong in a run-instructions README: what this is, how it was validated, and where it still falls short.

## Context

GitLab wants an agentic BI CLI: point it at a database, ask questions in plain English, get SQL + results back, including follow-ups. Their prototype (one bare prompt, GPT-5.4) had three problems — **wrong SQL**, **too slow** (~7s, need <3s P50), and **too expensive** at ~30,000 queries/day. This repo is the proof-of-concept addressing all three, plus the evidence it works.

## What I Built

- **[`src/baseline.py`](src/baseline.py)** — the customer's prototype as-is: one prompt, no schema, no retries.
- **[`src/agent.py`](src/agent.py)** — ours. 
  - Three differences: it sees the real `CREATE TABLE` schema in the system prompt
  - It calls SQL through a `run_sql` tool ([`src/tools.py`](src/tools.py)) instead of pasting SQL into free text, so a failed query's error can be handed back for another try (up to 4 attempts total)
  - It keeps the conversation, so follow-ups work.

## How I Validated It

```bash
uv run python -m src.eval
```

Runs both arms over all 10 questions in `data/dev_questions_with_answers.json`, **3 times each** — one run is too noisy to trust (a model can get the same question right once and wrong the next time). Grading compares each answer's result rows against the gold answer, ignoring row order, column names, and float rounding — there's more than one correctly-shaped query for most questions. ## Known Gaps & Assumptions

- **Schema only, no sample values.** The prompt has table/column names and types, not real data. `WHERE Country = 'USA'` can silently return zero rows if the real value is `'United States'` — no error, just a wrong-looking empty answer.
- **Retry only catches SQL that fails to run.** A query that executes but returns the wrong rows (a missed `JOIN` condition, wrong date filter) is never caught — nothing checks *correctness*, only "did it error."
- **No cap on result size or query time.** A query matching millions of rows, or an expensive `JOIN`, runs to completion and gets stuffed into the tool result and the terminal.
- **The read-only guardrail is a text check, not real enforcement.** [`_check_sql`](src/tools.py) blocks anything not starting with `SELECT`/`WITH`, but the DB connection itself is opened read-write — the check is what's stopping a write, not the database.
- **Conversation history is never trimmed.** Every question, SQL attempt, and full result set is kept for the life of the CLI session. A long session will eventually hit the model's context limit.
- **Only the entire schema, every time.** Works for Chinook's 11 tables; a database with hundreds of tables wouldn't fit in the prompt at all.
- **Single user, single process.** No concurrent sessions, and nothing persists between CLI runs — closing the CLI discards the conversation.
- **Two tool calls in one model turn breaks the session.** The agent loop only reads and answers the *first* tool call in a turn
  (`turn.tool_calls[0]` in [`src/agent.py`](src/agent.py)). If the model ever requested two, the second would get no response.
- **10 questions isn't enough to trust a single accuracy number.** That's why `eval.py` runs 3× and reports a range — but it's still a small, curated sample, not adversarial or representative of real usage.

## What I'd Tackle Next

- Fix the two-tool-call gap above (loop over all `tool_calls`, not just the first) before pointing this at a model/provider that supports it.
- Grow the dev set past 10 questions, including ambiguous ones.
- Add a row cap and query timeout before this goes near production traffic.
- Try a couple of other open models on Fireworks for a better cost/latency/accuracy trade-off than `gpt-oss-120b`.
